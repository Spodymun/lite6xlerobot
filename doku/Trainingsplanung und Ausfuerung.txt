1. Ausgangssituation und Zielsetzung

Ziel der Arbeit war es, für einen xArm Lite6 einen robusten, datengetriebenen Wurf zu realisieren, bei dem der Roboter:

einen Ball greift,

eine definierte Wurfbewegung ausführt,

und einen Zielpunkt (target_xy_mm) trifft.

Dabei sollte nicht:

eine klassische Trajektorienoptimierung,

oder reine Handparametrierung

verwendet werden, sondern ein lernendes Modell auf Basis des LeRobot-Frameworks, konkret mit der ACT-Policy (Action Chunking Transformer).

Die zentrale Fragestellung lautete:

Kann ein neuronales Modell lernen, aus einem Zielpunkt geeignete Bewegungsparameter (pos1, pos2, release_progress) abzuleiten, sodass ein stabiler Wurf entsteht?

2. Grundsätzliche Modellierungsentscheidung
2.1 Parameter-Policy statt Low-Level-Action-Policy

Sehr früh wurde entschieden, keine zeitdiskreten Servo-Actions zu lernen (z. B. Joint-Geschwindigkeiten), sondern eine Parameter-Policy:

Eingabe (Observation):

observation.state (Roboterzustand, 7D)

observation.task bzw. später observation.environment_state
→ enthält u. a. target_xy_mm

Ausgabe (Action, 13D):

[pos1_j1 … pos1_j6,
 pos2_j1 … pos2_j6,
 release_progress]


Diese Action beschreibt eine vollständige Wurfbewegung, nicht einzelne Zeitschritte.

👉 Vorteil:

physikalisch stabil

reproduzierbar

gut mit wenigen Daten lernbar

3. Datenerfassung (Recording)
3.1 Aufnahmeprozess

Für jeden Wurf wurde aufgezeichnet:

Ball lokalisieren

Ball greifen

Roboter in definierte Startpose fahren

Wurf ausführen

Release-Zeitpunkt erfassen

Landepunkt manuell labeln

Die Daten wurden im LeRobot-Format gespeichert:

records/throws/fs_<timestamp>_job_wurf_1/

├── meta/

│   └── tasks.parquet

4. Zentrales Problem: Dataset war nicht trainierbar

Nach der ersten Aufnahme war der Datensatz formal korrekt, aber nicht trainierbar mit ACT.

Typische Fehler:

observation.environment_state fehlte

Action-Shape passte nicht

Feature-Reihenfolge inkonsistent

info.json und Parquet-Schema nicht synchron

LeRobot verlangte ein Gym-Environment, obwohl offline trainiert wurde

5. Lösung: Reproduzierbare Dataset-Patch-Pipeline
5.1 Einführung einer automatischen Patch-Stufe

Es wurde ein idempotentes Patch-Skript entwickelt (patch_actions.py), das:

a) Action neu definiert
action = [pos1(6), pos2(6), release_progress]  # 13D

b) Task-Information einbettet
observation.environment_state
= concat(observation.state, observation.task)

c) Konsistenz erzwingt

Parquet-Spaltenreihenfolge == Feature-Reihenfolge

info.json und stats.json werden synchron angepasst

Backup aller Originaldateien

👉 Ergebnis:
Jeder neu aufgenommene Datensatz wird automatisch trainierbar gemacht.

5.2 Migration von job.json → throw_label.json

Ursprünglich wurden Wurfparameter aus einer externen job.json gelesen.
Das wurde bewusst geändert:

Neue Regel:

Alle relevanten Wurfinformationen liegen im Dataset selbst (meta/throw_label.json).

Vorteile:

Dataset ist selbstbeschreibend

kein implizites externes Wissen

bessere Reproduzierbarkeit

saubere wissenschaftliche Methodik

Warum keine zeitdiskreten Servo-Actions gelernt wurden
Kurzfassung (für Einleitung / Abstract)

Es wurde bewusst darauf verzichtet, zeitdiskrete Servo- oder Geschwindigkeitskommandos zu lernen, da diese für dynamische, kontaktlose Aufgaben wie Werfen zu instabil, datenintensiv und schwer reproduzierbar sind. Stattdessen wurde eine parametrische Aktionsrepräsentation gewählt, die eine gesamte Bewegung beschreibt.


1. Was wären zeitdiskrete Servo-Actions?
Zeitdiskrete Servo-Actions bedeuten typischerweise:
action_t = [Δq1, Δq2, …, Δq6]   oder   [dq1, dq2, …, dq6]

→ bei jedem Zeitschritt (z. B. 30–100 Hz)
→ das Modell entscheidet frameweise, wie sich der Roboter bewegen soll.
Das ist der klassische Ansatz in vielen RL-Papers.

2. Warum das für Werfen grundsätzlich problematisch ist
2.1 Werfen ist ballistisch, nicht feedback-getrieben
Beim Wurf:


Nach dem Loslassen gibt es kein Feedback mehr


Kleine Fehler akkumulieren sich extrem


5 ms zu früh / zu spät ≙ mehrere Zentimeter Abweichung


Ein Servo-Policy müsste:


extrem präzise Timing-Informationen lernen


unter Latenz, Jitter, OS-Scheduling funktionieren


➡️ realistisch kaum stabil lernbar auf echter Hardware

2.2 Hohe zeitliche Auflösung = massive Datenanforderungen
Beispiel:


1 Wurf ≈ 1 Sekunde


50 Hz Steuerung → 50 Actions


30 Würfe → 1500 Trainingsschritte


Aber:


nur ein einziger relevanter Moment (Release!)


98 % der Actions sind für das Ziel irrelevant


👉 Das Modell verschwendet Kapazität auf irrelevante Details.

2.3 Kausale Struktur wird verschleiert
Bei Servo-Actions:

„Warum hat der Ball diesen Punkt getroffen?“

ist im Modell nicht mehr direkt nachvollziehbar, weil:


Wirkung entsteht aus Summe vieler kleiner Actions


Keine explizite Repräsentation von:


Release-Zeitpunkt


Abwurfwinkel


Start-/Endpose




➡️ Keine Interpretierbarkeit
➡️ Keine saubere Generalisierung

3. Stabilität auf echter Hardware
3.1 Echtzeit ≠ Trainingszeit
Servo-Policies setzen voraus:


deterministisches Timing


garantierte Update-Raten


keine Paketverluste


In der Realität:


Python


ROS / Ethernet


nicht-echtzeitfähig


➡️ Ein Policy, das im Training funktioniert, scheitert oft real.

3.2 Sicherheitsaspekt
Servo-Actions:


können plötzlich hohe Geschwindigkeiten erzeugen


keine expliziten Constraints


Parameter-Policy:


pos1, pos2 sind vorvalidierte Posen


release_progress ∈ [0,1]


Bewegung ist vorher bekannt und begrenzt


➡️ wesentlich sicherer für reale Roboter

4. Warum Parameter-Actions für Werfen besser geeignet sind
4.1 Physikalisch sinnvolle Abstraktion
Ein Wurf wird vollständig beschrieben durch:


Startpose


Endpose


Release-Zeitpunkt


Das ist:


invariant gegenüber Abtastrate


robust gegen kleine Störungen


direkt kausal



4.2 Extrem niedrige Dimensionalität
AnsatzDimensionalitätServo-Actions6 × T (z. B. 300–600 Werte)Parameter-Policy13 Werte
➡️ Lernen wird drastisch einfacher

4.3 Bessere Generalisierung
Das Modell lernt:

„Wenn Ziel links → pos1 etwas anders → release früher“

statt:

„Bei Frame 37 +0.01 rad“

➡️ semantisches Lernen statt Steuerrauschen

6. Formulierungen für deine Arbeit (fertig verwendbar)
Methodik

Obwohl das LeRobot-Framework zeitdiskrete Aktionsrepräsentationen unterstützt, wurde bewusst eine parametrische Aktionsdarstellung gewählt. Zeitdiskrete Servo-Actions erfordern eine hochfrequente, latenzarme Ausführung und führen bei ballistischen Bewegungen wie dem Werfen zu instabilen Ergebnissen.


Diskussion

Die Entscheidung gegen zeitdiskrete Servo-Actions reduzierte den benötigten Datenumfang erheblich und erhöhte die Stabilität auf realer Hardware. Insbesondere für dynamische Bewegungen ohne Feedbackphase nach dem Release erwies sich eine parametrische Beschreibung der gesamten Bewegung als überlegen.


Fazit

Die Arbeit zeigt, dass eine geeignete Abstraktion der Aktionsräume entscheidender für den Lernerfolg ist als die Wahl des Lernalgorithmus selbst.
